# 1.3 리액트의 한계

리액트는 강력한 UI 라이브러리지만 모든 상황에서 최선의 선택은 아니다.
장점과 함께 한계도 이해해야 적절한 기술을 선택할 수 있다.

## 라이브러리로서의 불편함

리액트는 UI 구성에 집중하는 라이브러리다.
상태 관리와 라우팅과 데이터 요청 기능을 기본으로 모두 제공하지는 않는다.

개발자는 프로젝트에 맞는 서드파티 도구를 직접 선택하고 조합해야 한다.
이 구조는 자유도를 높여주지만 다음과 같은 문제를 만들 수 있다.

- 라이브러리 수가 많아진다.
- 도구마다 사용법이 다르다.
- 버전 호환성을 직접 확인해야 한다.
- 유지보수 책임이 개발자에게 커진다.

## Virtual DOM의 한계

Virtual DOM은 변경 사항을 계산한 뒤 실제 DOM에 필요한 부분만 반영한다.
하지만 이것이 언제나 성능 향상을 보장하는 것은 아니다.

- 상태 변화가 지나치게 자주 발생할 수 있다.
- 큰 화면에서는 비교와 렌더링 비용이 커질 수 있다.
- 컴포넌트 구조를 잘못 설계하면 불필요한 렌더링이 발생한다.

브라우저 엔진이 발전하면서 DOM 조작 비용도 줄어들고 있다.
따라서 Virtual DOM이 항상 필요한지에 대한 논의도 이어지고 있다.

중요한 것은 Virtual DOM이 좋고 나쁜지를 단순하게 판단하는 것이 아니다.
서비스의 상태 변화와 화면 구조에 맞는 방식을 선택하는 것이다.

## 리액트 생태계에 대한 의존성

리액트를 중심으로 발전한 라이브러리가 많다.
일부 도구는 리액트에서만 동작하도록 설계되어 순수 JavaScript나 다른 프레임워크에서 사용하기 어렵다.

이처럼 하나의 생태계 안에서만 기술이 발전하는 현상을 **갈라파고스화**라고 부르기도 한다.

처음부터 리액트를 사용하는 팀에는 큰 문제가 아닐 수 있다.
하지만 다른 프레임워크와 연동하거나 기술을 교체해야 할 때 선택의 폭이 좁아질 수 있다.

따라서 특정 생태계에만 의존하기보다 기술의 범용성과 프로젝트 목적을 함께 고려해야 한다.

## 복잡해진 프론트엔드 환경

현대 프론트엔드 개발은 하나의 기술만으로 완성하기 어렵다.

- UI 구성
- 상태 관리
- 라우팅
- 데이터 요청
- 사용자 경험
- 성능
- 접근성
- 보안

서로 독립적인 도구를 조합하는 과정에서 충돌이나 예외가 생길 수도 있다.
개발자는 각 도구의 사용법뿐 아니라 도구 사이의 관계와 전체 구조도 이해해야 한다.

따라서 처음부터 모든 기술을 익히기보다 실제 프로젝트에 필요한 기술부터 단계적으로 도입하는 것이 좋다.

## 라이브러리와 프레임워크의 차이

라이브러리는 특정 기능을 제공하는 코드 모음이다.
개발자가 필요할 때 직접 호출해서 사용한다.

프레임워크는 애플리케이션의 구조와 실행 흐름을 정해놓은 틀이다.
개발자가 정해진 규칙에 맞춰 코드를 작성하면 프레임워크가 필요한 시점에 코드를 호출한다.

> 라이브러리는 내가 호출하고 프레임워크는 나를 호출한다.

리액트는 UI 구성에 필요한 기능을 제공한다.
나머지 구조는 개발자가 직접 선택한다.

Next.js는 라우팅과 렌더링 방식과 디렉터리 구조 같은 전체 개발 흐름을 정해준다.

## 핵심 정리

리액트는 컴포넌트 기반 설계와 Virtual DOM과 Hooks를 통해 UI 개발 방식을 바꾸었다.
하지만 도구의 의존성과 생태계의 복잡성이라는 과제도 함께 만들었다.

기술은 유행만 보고 선택하는 것이 아니다.
프로젝트의 목적과 팀의 상황을 기준으로 선택해야 한다.
