# 1.2 리액트의 철학과 등장

## 리액트가 등장한 배경

리액트는 2013년 Facebook에서 공개한 오픈소스 UI 라이브러리다.

Facebook은 서비스가 커지면서 다음과 같은 문제를 겪었다.

- 화면 구조가 복잡해졌다.
- 상태에 따라 바뀌는 UI를 관리하기 어려웠다.
- DOM을 자주 수정하면서 코드 복잡성과 성능 부담이 커졌다.

리액트는 이런 문제를 해결하기 위해 **컴포넌트 기반 설계**와 **Virtual DOM**을 제시했다.

## 컴포넌트 기반 설계

컴포넌트는 화면을 구성하는 독립적인 부품이다.

버튼과 카드와 폼처럼 반복해서 사용하는 UI를 컴포넌트로 만들면 다음과 같은 장점이 있다.

- 코드를 재사용할 수 있다.
- 수정할 범위를 줄일 수 있다.
- 협업할 때 역할을 나누기 쉽다.
- 화면 구조를 이해하기 쉽다.

이 방식은 리액트 이후 여러 프레임워크와 플랫폼에서 널리 사용되고 있다.
Flutter의 위젯 구조도 비슷한 방향을 가진다.

## Virtual DOM

브라우저의 DOM은 HTML 문서를 객체로 표현한 구조다.
DOM을 직접 자주 수정하면 브라우저가 화면을 다시 계산해야 하므로 부담이 커질 수 있다.

리액트는 메모리에 Virtual DOM을 만들고 변경된 부분을 먼저 계산한다.
그다음 실제 DOM에는 필요한 변경만 반영한다.

이 과정을 통해 불필요한 DOM 변경을 줄이고 화면 업데이트를 효율적으로 처리한다.

## 리액트의 발전과 Hooks

초기 리액트는 클래스 컴포넌트를 주로 사용했다.
상태 관리와 생명 주기 처리를 클래스 문법 안에서 구현해야 했다.

이 방식은 컴포넌트가 복잡해질수록 재사용하기 어려웠다.
이를 개선하기 위해 함수 컴포넌트와 Hooks가 등장했다.

Hooks는 2018년에 발표된 뒤 2019년에 정식으로 도입되었다.
함수 안에서 상태와 생명 주기를 선언적으로 다룰 수 있게 해주었다.

현재는 대부분의 프로젝트가 함수 컴포넌트를 사용한다.
클래스 컴포넌트는 주로 기존 레거시 코드를 다룰 때 만난다.

## 렌더링 방식의 변화

과거에는 서버가 HTML을 만들어 브라우저에 보내는 방식이 일반적이었다.
이후 클라이언트에서 화면을 만드는 CSR이 널리 사용되면서 프론트엔드의 역할이 커졌다.

최근에는 CSR만 사용하는 방식에서 벗어나 SSR과 SSG를 함께 사용하는 하이브리드 방식도 활용한다.
리액트는 Next.js 같은 프레임워크와 결합해 다양한 렌더링 전략을 지원한다.

이를 통해 초기 로딩 속도와 검색 엔진 최적화 같은 요구사항에도 대응할 수 있다.

## 리액트 개발 환경과 생태계

리액트는 혼자 모든 기능을 제공하는 도구가 아니다.

- ES6 이상의 JavaScript 문법
- Babel과 Webpack 같은 빌드 도구
- TypeScript의 정적 타입 검사
- 라우팅과 상태 관리와 폼 처리를 위한 서드파티 라이브러리

React Router는 라우팅을 담당한다.
Redux와 Zustand는 상태 관리를 돕는다.
React Hook Form은 폼 처리를 단순하게 만든다.
Material UI와 shadcn/ui는 재사용 가능한 UI를 구성하는 데 도움을 준다.

이처럼 리액트는 큰 생태계와 활발한 커뮤니티를 바탕으로 개발 생산성을 높인다.

## 핵심 정리

리액트의 핵심 철학은 UI를 독립적인 컴포넌트로 나누고 필요한 부분만 효율적으로 갱신하는 것이다.
